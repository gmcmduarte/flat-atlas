## Architecture

**D-05 The pipeline always computes in DuckDB + Parquet; PostgreSQL is a serving copy loaded from a release.** *Alternatives:* SQLite for the pilot then a port to Postgres; Postgres everywhere including the laptop. *Reason:* one code path in both stages; DuckDB handles the full field (hundreds of thousands of works, millions of citation edges) on one machine; no ORM or dual SQL dialect; the migration to the server becomes "load a release".

**D-06 A versioned release (Parquet + manifest) is the contract** between pipeline, static site, server database and Zenodo. *Reason:* the site shows exactly what the dataset contains; rollbacks are trivial.

**D-07 Core journals that publish much non-FLAT material are Tier B.** Information and Computation, Acta Informatica, Fundamenta Informaticae and Natural Computing are filtered by the scope rule with a lenient threshold; they are not included wholesale. *Alternative:* include everything from the core list. *Reason:* "comes from automata and formal languages" would be diluted by unrelated logic, complexity and evolutionary-computing papers. **Needs confirmation** (OPEN-QUESTIONS Q3).

**D-08 Stack for the pipeline.** Python 3.12 (pinned; the system Python 3.15 is too new for the ML wheels), uv, Typer, pydantic, httpx, DuckDB, pyarrow, rapidfuzz; ruff, pytest, pre-commit, gitleaks, GitHub Actions. *Alternatives:* Poetry/conda; pandas-centred code; Snakemake/Prefect/Dagster for orchestration. *Reason:* uv gives a fast, locked, reproducible environment; a small hand-written stage runner is enough for a linear pipeline and has no service to maintain.

**D-09 Frontend: SvelteKit + TypeScript with the static adapter; Sigma.js v3 + graphology for the map; MiniSearch for pilot search; Observable Plot for charts.** *Alternatives:* Astro (excellent for content sites, weaker for an app-like map with shared state); Next.js/React (heavier, more boilerplate, static export has more limits); plain Vite + vanilla (less structure); D3 canvas or Cosmograph or deck.gl for the map. *Reason:* small bundles, simple state for map + slider, static output for Pages and the same app in API mode. Sigma is kept behind one component because, with a precomputed layout and at most about 150 visible nodes, the renderer is replaceable.

**D-10 Map layout is precomputed in the pipeline, not in the browser.** *Alternative:* live force simulation. *Reason:* deterministic and stable across visits and across the time slider; cheap on phones; avoids the hairball because the pipeline controls aggregation.

**D-11 Client-rendered entity pages with a static fallback (SPA mode); only topic and venue pages are prerendered.** *Alternative:* prerender every paper page. *Reason:* hundreds of thousands of HTML files do not fit GitHub Pages (1 GB) or sensible build times.

**D-12 Server stack: Docker Compose, PostgreSQL + pgvector, FastAPI with plain SQL, Caddy.** *Alternatives:* Kubernetes (overkill); Django (admin for free, but a heavier app and ORM); nginx + certbot (more to configure). *Reason:* smallest number of moving parts a single maintainer can restore from a runbook.

**D-13 No workflow engine, no vector database, no message queue.** Numpy/DuckDB for similarity at this scale; pgvector only if "similar papers" is offered.

## Scope, taxonomy, tagging

**D-20 Inclusion rule = venue tiers + a multi-signal scope score + field guards + at most two expansion rounds** (PLAN §6), tuned by automatic hold-out and background tests. *Alternatives:* venue lists only (misses FLAT papers in TCS/JCSS and older journals); keywords only (floods from verification and combinatorics); citation proximity only (drifts).

**D-21 The topic DAG lives in git as YAML (`taxonomy/topics.yaml`); the pipeline only proposes changes.** *Reason:* reviewable diffs, community suggestions as pull requests, no silent taxonomy drift.

**D-22 Own topic names and descriptions; CCS and MSC appear only as cross-reference codes.** *Reason:* MSC2020 is CC BY-NC-SA and CCS is ACM copyright.

**D-23 SPECTER2 is the paper embedding** (precomputed vectors from Semantic Scholar where available, the same public model locally otherwise). *Alternatives:* general sentence-transformers models (better for short queries, worse for paper–paper similarity), SciNCL, newer long-context encoders. *Reason:* free precomputed vectors for most works and identical geometry locally. A small general model may be added for topic-description matching if the P1-07 experiment favours it.

**D-24 Tagger v1 is a transparent weighted fusion; v2 (weak supervision) is adopted only if it wins on the automatic checks.** *Reason:* explainable provenance first; learned weights only with evidence.

**D-25 Propagation runs exactly one extra pass.** *Alternative:* iterate to convergence. *Reason:* deterministic, incremental-friendly, avoids over-smoothing topics along citation chains.

**D-26 The local LLM is off by default and never an override.** Its output is one more signal for low-confidence works only. *Reason:* zero-cost and reproducibility constraints; no acceptance criterion depends on it.

**D-27 Evaluation uses anchor papers, agreement, coherence, venue sanity, stability and spot-check reading**, never a hand-labelled test set. Anchors are drafted by Fable, verified against real identifiers, and reviewed together with the taxonomy.

## Harvest core (P0-02)

**D-39 The HTTP cache stores gzip JSON per request under `data/raw/<source>/<hash[:2]>/`.** Each entry is `<hash>.json.gz` plus `<hash>.meta.json` (status, sanitised URL, `fetched_at`, rate-limit headers). The key hashes method, URL, sorted params and body, and **excludes** the API key and the contact email, so rotating a key never invalidates the cache and no key can reach disk. Data is written first and metadata last; a crash in between is just a cache miss. A 404 or 410 is cached as a result (`data: null`) so missing DOIs are not asked again; any other 4xx raises. *Alternative:* store raw bytes (needed if a source returns XML; revisit with zbMATH OAI-PMH in P6-02).

**D-40 The daily budget lives in a JSON ledger, not in DuckDB.** `data/raw/<source>/_budget.json` maps UTC day to spent micro-dollars. *Reason:* `http.py` stays independent of the warehouse, and a running harvest holds the DuckDB write lock. This avoids a new table, so PLAN §4.6 is unchanged. Every real attempt is charged, retries included (conservative); cache hits and free call kinds cost nothing. A call that would exceed the budget raises `BudgetExhausted` before it is sent.

**D-41 Retry and rate-limit policy.** Hand-written, with injectable clock and sleep so tests never wait (`tenacity` is a dependency from P0-01 but is not used). Retry on 429, 500, 502, 503, 504 and transport errors, at most `max_attempts` (6) with back-off 1, 2, 4, 8, 16 s; a `Retry-After` (seconds or HTTP date) replaces the back-off. A `Retry-After` above `max_retry_wait_seconds` (300) is refused rather than slept through, so the job stops and can be relaunched. Crossref's `x-rate-limit-limit` and `x-rate-limit-interval` can lower the rate, never raise it. The client is synchronous; the profile's `concurrency` is not used yet.

**D-42 Secrets never reach logs or errors.** Keys go on the wire only (query parameter or header, per `auth` in `config/sources.yaml`); they are not in the cache key, cache files, error messages or logged URLs. Errors raised from transport failures are re-raised without the original exception (`from None`), because httpx messages can echo the URL. The `httpx` and `httpcore` loggers are forced to WARNING (httpx logs request URLs at INFO). Registered secrets are also replaced by `***` by the log formatter. OpenAlex key parameter name `api_key` is unverified.

**D-43 Profiles and source table.** `config/sources.yaml` holds per-source `requests_per_second`, `burst`, `batch_size`, `daily_budget_usd`, `costs`, `auth` and `mailto_param`; `config/profiles/<name>.yaml` follows PLAN §5.4. Data root precedence: `--data-root` argument, `FLATATLAS_DATA_ROOT`, profile; relative paths are relative to the repository root. `server.yaml` values are placeholders until P3-00; `active_venues: all` means every venue in `config/venues.yaml`. Semantic Scholar `batch_size` starts at 100, not the 500 PLAN recalls (unverified).

**D-44 `paged()` is at-least-once.** The cursor of page N+1 is stored when the consumer asks for it, after finishing page N. A kill during page N repeats page N on resume (free, because it is cached), never skips it. Job states: `running`, `interrupted`, `done`; a `done` job yields nothing unless `restart=True`.

**D-45 `flatatlas status` is a plain command, not a group.** `COMMAND_GROUPS` keeps all 13 names; `PLAIN_COMMANDS` lists those that are commands. Status opens the warehouse read-only and says so if a running job holds the write lock.

## Venue registry and IDs (P0-03)

**D-46 Atlas IDs are a kind prefix plus 10 base32 characters of a SHA-256 hash of the anchor.** Format `W` / `A` / `V` / `E` + 10 characters of RFC 4648 base32 (A–Z, 2–7), e.g. `WT3SYS5P77T`. The hash input is `kind`, normalised source and anchor id (DOI anchors are lower-cased and lose their `doi:` / `https://doi.org/` prefix). *Why 10 and not 8:* 8 characters (40 bits) give about a 4% chance of at least one collision among 300,000 works; 10 (50 bits) gives about 0.004%. If a collision happens anyway, the new ID takes one more character; the registry is part of every release, so the result is stable. *Alternatives:* random IDs (not reproducible from the anchor), sequential numbers (leak order, clash between rebuilds). Values are pinned in `tests/unit/test_ids.py`: changing the scheme means breaking published IDs.

**D-47 One anchor per registry row; secondary identifiers are the resolve stage's job.** `core_id_registry` keeps the single anchor an ID was minted from. `mint_from()` returns an existing ID if any given anchor was already minted (an ID never changes because a better anchor appeared), otherwise mints the preferred anchor (PLAN §4.1 order). Linking a work to its other identifiers, and merging two IDs that turn out to be one work, happens in P1-04 through `merge()`. The registry file is `data/warehouse/core_id_registry.parquet`. Merge rules: same kind only, a merge into an ID that leads back to the loser is refused, a merged-away ID keeps its row and its anchor (so the anchor never gets a new ID).

**D-48 Venue entries carry `verified: {dblp, openalex}` dates; `null` means "from memory".** Added to the PLAN §7 example together with `issn`, `publisher`, `special_issue_of`, `expected_topics` and `homepage` (the prompt's field list). `flatatlas venues check` warns about unverified entries; `verified.dblp` without a `dblp_stream` (or `verified.openalex` without source IDs) is an error. Rule for later sessions: **do not harvest a venue whose `verified.dblp` is null.** `venue_facts.yaml` is `venues: {<id>: {<year>: {core_rank|submissions|accepted: {value, source_url, note}}}}`; a value without a `source_url` is rejected. `venues check` also fails when a profile's `active_venues` names an unknown venue.

**D-49 DBLP data comes from the XML dump, not the API.** On 2026-11-15 `dblp.org` and both mirrors answer API requests from scripts with HTTP 202 and an Anubis proof-of-work page. Solving it would bypass bot detection, so it is not attempted. Guilherme downloads `dblp.xml.gz`, `dblp.dtd` and the `.md5` by hand into `data/raw/dblp-dump/` (git-ignored); the code only reads them (CC0 metadata, CLAUDE.md rule 2). `config/sources.yaml`'s `dblp` entry stays but is unused. Consequences: P1-01 becomes "parse from the dump" (prompt rewritten in this PR), the DBLP half of P4-01 shrinks to scaling and incremental refresh, and the ≤ 1 request/s DBLP policy no longer applies. *Alternative not taken:* ask DBLP to allow-list a client (can still be done, but the dump is needed for the bulk load anyway). Refreshing the data means downloading a new dump by hand.

**D-50 How the dump is read and indexed.** `flatatlas.dblp_dump` streams the dump through `gzip` and `xml.etree`; the DTD is never loaded as an external resource: its named entities are read with a regular expression and given to the parser as a dictionary (no resolution of external resources, nothing written to disk). `flatatlas venues scan-dump` verifies the MD5 and writes `data/raw/dblp-dump/stream_index.json` for the streams in `venues.yaml` (about 100 s); `venues show` reads it. An *edition* is a `proceedings` record or a key cited in papers' `crossref`; its **year is the key's last part** (`conf/dlt/2019`), not the record's `year`, which is the publication year (`conf/dlt/2025` has 2026). **Two venues may share one DBLP stream** (WIA and CIAA are both `conf/wia`; DCAGRS and DCFS both `conf/dcfs`) if each states `first_year` and the `first_year`/`last_year` ranges do not overlap; `venues check` enforces this. `first_year` of a venue is the first edition inside its stream, which for DCAGRS (2001) is later than the series' real start. Rule from D-48 stands: do not harvest a venue whose `verified.dblp` is null; all five pilot venues are verified (2026-11-15, dump MD5 `4316d8f5`).

**D-51 DCFS 2009 and 2010 are added; keys DBLP files in the wrong place are config.** Guilherme's call (P1-01, 2026-11-15): the 11th and 12th DCFS workshops, which DBLP holds only as EPTCS volumes under CoRR (`journals/corr/abs-0907-5257`, EPTCS 3; `journals/corr/abs-1008-1270`, EPTCS 31), are DCFS editions. `venues.yaml` gets `extra_editions: [{key, year, note}]` per venue (key of the `proceedings` record, year of the meeting; `venues check` rejects a key inside the venue's own stream or listed twice). Their papers are the `inproceedings` records whose `crossref` is that key (verified in the dump: 8 of the first 10 hits). The parser therefore also reads the `journals/corr` stream, but keeps only records that cite an extra edition. The mirror image is `excluded_editions: [key]`: `conf/dlt/2000` (36 papers of a Kyoto meeting that DBLP files in the DLT stream, found in P0-03) is excluded, so its papers are not DLT papers. Editions and papers left out are counted in the run log. *Alternative not taken:* leave the two volumes out (it would have put holes in the DCFS timeline and the venue-analytics page).

**D-52 Author PIDs come from the person records; no guessing.** Paper records carry names only (`Name 0001` for homonyms). A `<www key="homepages/<PID>">` record lists the person's names (the first is the primary one); each name printed on a kept paper is looked up among them. In the 2026-11-15 dump every name on a pilot paper matched exactly one person, so no PID is guessed or fuzzy-matched; if a name matches no record or two records, its PID is null and it is counted (`names_without_pid`, `names_ambiguous` in `ops_run_log`). The person records come after the papers in the dump, so one pass suffices; the parser checks the order and does a second pass over the person records if a future dump changes it. The author's display name drops DBLP's four-digit homonym suffix (`Bo Cui 0001` becomes `Bo Cui`); the printed form stays in `name_variants` and in `stg_dblp_authorship.name_raw`. ORCID comes from the person record (`<url>https://orcid.org/…</url>`, or a `note type="orcid"`), else from `<author orcid="…">` on a paper; a conflict is counted and the person record wins. Person records also list zbMATH, Wikidata, Google Scholar and affiliation links; they are not stored here (parking lot).

**D-53 Staging layout of the DBLP parse.** `flatatlas parse dblp` replaces four DuckDB tables and writes a Parquet copy of each in `<data>/warehouse/staging/`: `stg_dblp_edition`, `stg_dblp_paper`, `stg_dblp_authorship` (positions are 1-based), `stg_dblp_author`. They hold the venues of the *last* run (a run with `--venue` replaces all four), always with the venue's predecessors. A paper's `doi` is the publisher's DOI from `ee`; an arXiv DOI (`10.48550/arxiv.…`) is used only if there is nothing else, and all DOIs stay in `dois`; DOIs are lower-cased. Titles are stored without DBLP's trailing period, plus `title_norm` (lowercase, no accents, punctuation or LaTeX). `is_front_matter` and the rule that set it (`front_matter_rule`) come from `config/dblp_parse.yaml`; flagged rows stay in the table. The run log records the dump's MD5, file date and newest record date, so a rerun on a newer dump is visible. Per-edition paper counts are compared with the stream index of `venues scan-dump`.

**D-54 The web skeleton reads a committed fixture through `PUBLIC_DATA_DIR`; types are hand-written for now.** `web/static/data-fixture/` (5 topics, 10 works, 5 authors, 1 venue, a map layout) is committed and follows PLAN §11.2; `PUBLIC_DATA_DIR` (default `data-fixture`) names the folder under `static/` that `StaticDataSource` reads, so the pipeline's export (`static/data/`, git-ignored, PLAN §11.1) replaces it with one setting. Fixture IDs are plainly fake (`WFIXTUREAAA`, `AFIXTUREAAA`, `VFIXTUREAAA`: D-46 format, but spelling FIXTURE) and every record has `fixture: true`. `src/lib/data/types.ts` is written by hand with snake_case fields equal to the exported column names; generating it from the schema (PLAN §11.1) waits until the export format exists (P1-09). The works and authors shard is the first two hex characters of the SHA-256 of the ID (`shardOf`); the exporter must use the same rule. *Alternative not taken:* put the fixture in `static/data/`, which PLAN §11.1 keeps git-ignored.

**D-55 Web tooling.** SvelteKit 3 and Vite 8, created with `sv` (config lives in `vite.config.ts`; `$app/env/public` and `src/env.ts` replace `$env/*`). `adapter-static` with `fallback: '404.html'`; `kit.paths.base` comes from `BASE_PATH` at build time (`/flat-atlas` in CI, empty locally). Root layout sets `prerender = true`; topic pages are prerendered from `entries()`, which reads the data folder's `topics.json`; any URL that was not prerendered is served by `404.html` and rendered in the browser. Links use `resolve()` from `$app/paths`. Tests: Vitest with two projects, `server` (node; `StaticDataSource` against the fixture on disk) and `client` (jsdom with Testing Library; component tests). *Not taken:* the `sv` default of Vitest browser mode with Playwright, because it needs a Chromium download on every machine and in CI for one small component test; real-browser checks are done with the browser preview. CI runs Node 24 (the tooling needs 22.17 or newer).

**D-56 Pages deploys on every push to `main`.** `.github/workflows/pages.yml` builds `web/` with `BASE_PATH=/<repository name>` and deploys with the official Pages actions; the repository setting Pages > Source = "GitHub Actions" is a one-time manual step (P0-00). `ci.yml` has a separate `web` job (check, lint, test, build with a base path) next to the Python job. `.gitignore` re-includes `web/src/lib/data/`, which the `data/` rule (local pipeline data) would otherwise hide.

**D-57 OpenAlex lookups: DOI batches of 100, then a capped title search.** `flatatlas harvest openalex` asks `filter=doi:https://doi.org/a|...` with 100 DOIs per call (the maximum; 101 gives HTTP 400) and `per_page=200`, then searches papers without a usable DOI with `filter=title.search:<words>,publication_year:<y-1>|<y>|<y+1>` (USD 0.001 a call, same as `search=` but it returned one precise hit instead of thousands). The search is capped (`--max-title-searches`, default 400; the pilot needs 315) and goes through the budget guard. A title hit is accepted at normalised-title similarity of at least 0.95 (rapidfuzz ratio) and a year within 1; each lookup row stores `match_method` and `match_confidence` (rule 4). DOIs with a comma or a pipe go to title search because they would break the filter syntax. `from_updated_date` is not available on the free key (HTTP 429), so incremental refresh re-fetches by DOI.

**D-58 Harvest stores nothing; parse reads the cache.** The harvest only fills the `SourceClient` disk cache (and the cursor in `ops_harvest_state`). `parse openalex` rebuilds what was asked from the cached request URLs (`SourceClient.iter_cached`, `cached`, offline): a DOI that was asked and not returned is "fetched, not found"; a DOI never asked is "not fetched". Only answers whose `select=` equals the current `SELECT` count, so changing the field list means re-harvesting and old probes are ignored. A `--limit` run followed by a full run needs no bookkeeping.

**D-59 Staging layout of the OpenAlex and Crossref parse.** Tables in `<data>/warehouse/staging/` (DuckDB + Parquet), each replaced whole by its parse command: `stg_openalex_lookup` (one row per DBLP paper: lookup kind, fetched, matched work, method, confidence), `stg_openalex_work` (one row per OpenAlex work), `stg_openalex_authorship` (author x institution; an author without institution has one row with nulls), `stg_openalex_reference` (citing, cited), `stg_openalex_topic` (`kind` = topic or keyword), `stg_reference_candidates` (cited works that are not pilot works, with the number of pilot papers citing them), `stg_crossref_work`. Abstract text goes to the local-only `local_abstract` (`warehouse/local/`), **keyed by `dblp_key`, not `work_id`**, because work IDs do not exist before the resolve stage (P1-04); each parse replaces only its own `source`. Crossref is asked only for DOIs OpenAlex lacks or has without abstract, first page, date or references (that is almost every DOI, because abstracts are missing), and never for `10.48550/` (arXiv, DataCite).

**D-60 The coverage report is `flatatlas evaluate coverage`, committed under `reports/`.** It is computed from the warehouse tables (no network) and written to `reports/coverage-<profile>.md` in the repository, so it can be read in a PR. Shares are of all DBLP papers in the cell; partial runs and missing stages are flagged in the text; the DOIs OpenAlex did not return are listed.

## Tagging redesign (2026-11-16): D-61 to D-66 approved by Guilherme; D-67 not active

Drafted from `docs/notes/tagging-redesign-brief.md`. D-61 to D-66 were approved by Guilherme on 2026-11-16. **D-67 is not approved**: it stays inactive until Guilherme changes its status line himself.

**D-61 (approved 2026-11-16; amends D-27) A small hand-reviewed labelled set is allowed, for training and held-out evaluation.** `taxonomy/gold.yaml` holds 400–600 works labelled at level 0 and level 1 (multi-label), drafted by Claude and reviewed work by work by Guilherme (2–3 hours). The sample is random with a fixed seed, stratified by venue, decade and has-abstract, and never chosen by tagger output; a top-up of at most 100 works for thin level-1 topics is marked as such and is training only. A hash of the work ID fixes the split: two thirds train, one third held-out. The held-out third is used only to compare methods and to report precision and recall; it is never used for training, calibration, threshold tuning or seed sets. 50 works are labelled blind first, to measure how much the draft steers the reviewer. The file is human-edited (rule 5), versioned with `taxonomy_version`, and its reviewed entries are never overwritten (rule 6). The other checks of D-27 (anchors, agreement, coherence, venue sanity, stability, spot checks) stay. *Alternative:* keep D-27 as it was. *Reason:* anchors are famous, easy papers and flatter the tagger; without real labels there is no precision or recall, and nothing can learn how much to trust each signal. *Cost:* €0 and about 3 hours of Guilherme's time, repeated in part at each taxonomy version.

**D-62 (approved 2026-11-16; note on D-02) Paper tagging stays fully automatic.** The labelled set trains and measures the tagger. A label in `gold.yaml` never becomes a published tag directly: labelled works are tagged by the same pipeline as every other work, and the site shows only pipeline tags with their confidence and provenance. *Reason:* one rule for all works; a labelled paper that the tagger gets wrong is useful evidence and must stay visible.

**D-63 (approved 2026-11-16; supersedes D-26 and the "v1 hand weights, v2 weak supervision" order of PLAN §9.4) The tagger is a cheap-to-expensive cascade.** (1) Signals and a shortlist of about 8 topics for every work; (2) a learned fusion model (LightGBM or logistic regression) over the signals and context features (has abstract, number of references, topic size, topic level, parent probability), trained on gold-train and silver labels, with isotonic calibration; (3) a **local** decision model (an open 4–9B model read for option probabilities, no text generated) only for works that step 2 is unsure about, as one more signal and never an override; (4) a small distilled classifier so that weekly new works never need step 3. The hierarchy is soft: a child's score is conditioned on its parents' probabilities and no work is routed away from a branch. Embedding scores are per-topic percentiles, never raw cosines. Noisy-or fusion and a top-down classifier are built as baselines, and the shipped method is chosen on the held-out third: a more complex method is adopted only if the bootstrap interval of the paired difference excludes zero and no hard check gets worse. Kept from before: one propagation pass (D-25), most-specific selection, threshold 0.35 and at most 6 topics as starting values, derived ancestor rows, artefacts frozen per `tagger_version`. *Alternatives:* hand-weighted noisy-or alone (cannot learn per topic or per paper type); a purely top-down supervised classifier (errors cascade, needs about 9,000 labels for 300 topics, handles several parents badly); a text-generating LLM returning JSON (slower, hard to calibrate). *Reason:* effort is spent only where cheap signals are unsure, and every choice is made by measurement. *Cost:* €0; step 3 is hours of local computing, run overnight (rule 7).

**D-64 (approved 2026-11-16) Models read a composite text, because abstracts are mostly missing.** `title · venue · year · titles of up to 10 references (fixed selection rule) · abstract if present · Semantic Scholar TLDR if present`. A new signal `lex_refs` matches topic phrases in reference titles. For embeddings the Semantic Scholar SPECTER2 vector is used when it exists; otherwise the local model embeds this text (D-23 unchanged). Abstracts and TLDRs remain local-use data (rule 2): the composite text lives only under `warehouse/local/` and is never exported. Titles of cited works outside the corpus are fetched once through `flatatlas.http` inside the free budgets (P1-05). *Reason:* 6 % of pilot works have an abstract and 88 % have a reference list; what a paper cites describes it better than a title alone.

**D-65 (approved 2026-11-16) Schema and config changes that follow.** `tag_signal` gains `lex_refs`, `dm_l0`, `dm_child`, `distil`, the context features and `shortlisted`; `tag_work_topic.provenance` gains `models` (file hashes); new local-only cache `local_decision`; new table `eval_gold` loaded from `taxonomy/gold.yaml`; `config/tagger.yaml` gains the method, the unsure band, the decision-model settings (model file, hash, option orders, cap on questions) and the distilled-model settings. OpenAlex and author keywords are not used as a signal until their precision has been measured on the labelled set. PLAN §4.4, §9 and §16 are updated.

**D-66 (approved 2026-11-16) D-12 and D-13 stand: no Redis, no vector database.** Tagging compares about 300,000 works with about 500 topics in one numpy matrix product (seconds). "Similar papers" and hybrid search at the server stage use PostgreSQL full-text search plus pgvector, merged by reciprocal rank fusion in SQL; the static pilot ships neighbours precomputed in the pipeline as JSON (parking lot until a session takes it). *Alternative:* Redis 8.4 hybrid search. *Reason:* one more service to run and everything held in RAM, for a result the planned stack already gives.

**D-67 (PROPOSED, NOT ACTIVE; needs its own explicit approval) A narrow, capped exception to hard rule 3 for a hosted decision model.**
*Status: not approved. Hard rule 3 ("no paid APIs, no paid services") is in force unchanged. No session may write a client for a hosted model until this line reads "approved by Guilherme on <date>".*
If approved, the exception would allow one hosted decision model (candidate: Microsoft-Decision-1 on Azure) in the batch tagging step only, under **all** of these conditions:
1. **Evidence first.** The local decision model has been measured on the held-out third, and the question is whether the hosted one is better. The first use is a comparison on the 2,339 pilot works (about $0.10 at the unverified price). It is adopted for a field run only if it beats the local model by a margin whose bootstrap interval excludes zero.
2. **Hard cap in code.** A spending counter and cap in `config/`, enforced in `flatatlas.http` like the OpenAlex budget guard: clean stop before the cap, run log of tokens and money. Proposed caps: $1 for the pilot comparison, $15 in total for a full-field tag, $1 a year for increments. Guilherme sets the numbers when approving.
3. **Verified terms.** Price, free tier, data-retention and training-use terms are read on the provider's official pages and recorded in `docs/notes/sources.md` before the first call (today they are known only from secondary sources).
4. **Public metadata only.** Titles, venue, year and reference titles may be sent. Abstracts and TLDRs are **not** sent (rule 2); sending them would need a further decision.
5. **Pinned version, shuffled options, own calibration.** No `latest` alias; calibration checked on gold-train as for the local model.
6. **Batch only, never per view or per user.** Weekly increments stay on the distilled local classifier.
7. **Reversible.** The hosted answers are one more signal with their own provenance; turning the exception off falls back to the local model without re-tagging everything.
What approval would change: the wording of hard rule 3 in `CLAUDE.md` ("except the capped decision-model exception of D-67"), `.env.example` (key name), `config/sources.yaml` (cap), and one build step in P4-05. *Alternative, and the current plan:* stay local and free. *Recommendation:* decide only after P1-08 shows whether the local model is good enough; if it is, this entry can be closed as "not needed".

## P1-03 (2026-11-16): Semantic Scholar and embeddings

**D-68 Semantic Scholar lookups: DOI batches of 500, then a capped title match.** `POST /paper/batch` with `DOI:<doi>` IDs, 500 per call (501 gives HTTP 400). S2 does not accept `DBLP:<key>` IDs (it answers null for papers it holds), so papers without a DOI, and papers whose DOI came back null, go to `GET /paper/search/match` (one call each, capped at 1,000 by `--max-title-matches`, key order). A hit is accepted at normalised title similarity of at least 0.95 and a year within 1 of the DBLP edition, the OpenAlex rule of D-57. Status per paper is `matched`, `not_found` (every route that applies was tried) or `not_fetched`. S2 often returns another version of the same title (354 of 2,260 matches carry another DBLP key: the journal or CoRR version): the match is kept and the other key stored in `stg_s2_lookup.s2_dblp_key`; deciding whether it is the same work is P1-04's job (§8.2). The per-edge "influential" flag is not available (`references.isInfluential` gives HTTP 400 in a batch), so `core_citation.is_influential` stays null until a later session reads the datasets or `/paper/{id}/references`; the per-paper `influentialCitationCount` is stored.

**D-69 The cache keeps the body of a POST (amends D-58).** `SourceClient` writes `request_body` into the metadata of a cached POST answer and returns it as `Response.request_body`. A parse stage can then tell which IDs were asked, and aligns the answer list with them by position (S2 returns one item or null per ID, in order). Without it a `--limit` run followed by a full run could not tell "asked and not found" from "never asked".

**D-70 `local_embedding` and `local_abstract` are keyed by `dblp_key` until P1-04; one vector per paper (amends PLAN §4.2).** `local_embedding(dblp_key, model, source, s2_corpus_id, input_kind, abstract_source, vector FLOAT[768])`, local-only (`warehouse/local/local_embedding.parquet`, a fixed-size list; DuckDB reads the raw Parquet as `FLOAT[]`, the warehouse table as `FLOAT[768]`). Exactly one row per paper: `source` is `s2` or `local`, S2 ranks first, and every write enforces it, so re-running `parse s2` after a later harvest replaces a local vector with S2's. `local_abstract` keeps one row per paper and source; `flatatlas.abstracts.best_abstracts()` applies the priority OpenAlex, then Semantic Scholar, then Crossref. TLDR text sits in `stg_s2_paper.tldr`; staging tables are never exported (rule 2).

**D-71 Local SPECTER2: model, input, installation.** Base `allenai/specter2_base` plus the proximity adapter `allenai/specter2` through the `adapters` library, first-token state, 768 floats. Input `title[SEP]abstract`, and the title alone when there is no abstract (the model card's trailing separator was measured and is slightly worse against S2's vectors: 0.958 against 0.960). torch, transformers and adapters are the optional extra `ml` (`uv sync --extra ml`), imported lazily, so the base install and the base CI job never load them (a test checks it). The weights come through the Hugging Face libraries, not `flatatlas.http`: they are a model download, not a source API, so rule 8 is read as covering the data sources only. Device from the profile, `cpu` when `mps` or `cuda` is missing. The encoder refuses to run if no adapter is active (a plain base model would give vectors that do not match S2's: 0.939 against 0.997). Finished batches are cached by (model, text) under `data/cache/embed/`, so a killed run loses at most one batch.

**D-72 Semantic Scholar is called at 0.5 request/s with 10 attempts per request (amends D-41's 1/s).** The documented 1 request/s is not what the key gets: 429s came on 15 to 25 % of calls even at 5 s spacing, and about 1.3 to 2 per success at 1/s and at 0.5/s; fewer fields did not help. Two runs at 1/s and six attempts died after six 429s in a row. With 0.5/s and ten attempts (about 4 minutes of back-off) the resumed run finished: 637 title matches in 1 h 53 min, about 11 s each. Nothing to gain from a lower rate, so the rate is a politeness choice; the attempts are what matter.

## P1-04 (2026-11-16): entity resolution and the core tables

**D-73 Title similarity is the token-sort ratio, not the token-set ratio (amends PLAN §8.1).** `rapidfuzz.fuzz.token_set_ratio` returns 100 whenever the words of one title are contained in the other's ("Isometric Words" against "Hypercubes and Isometric Words Based on …"), so a paper would match any longer title. The token-sort ratio (words sorted, then compared) is order-insensitive and still penalises extra words. Titles are folded first (lower case, no accents or punctuation, dashes unified) and "(extended abstract)", "full version" and the like are removed (list in `config/resolve.yaml`). The §8.1 limit stays 0.93.

**D-74 How versions are merged (specifies PLAN §8.2; thresholds in `config/resolve.yaml`).** Candidates: share ≥ 1 DBLP PID, the later version 0 to 6 years after the earlier one, title similarity ≥ 0.75 (below that they are different papers; this pre-filter is what keeps follow-up papers by the same authors out), different editions. The plan said "different venues"; the real duplicates in the pilot sit in one venue's consecutive editions, so the rule is "different editions" and the score decides. Score = 0.45 title + 0.30 author Jaccard + 0.15 embedding (cosine 0.7 → 0, 1.0 → 1) + 0.10 "extra", the strongest of: both papers resolve to one S2 or OpenAlex record (1.0), the S2 record of one lists the other's DBLP key (0.5), and, **only when the two versions are different kinds** (conference paper, journal article), the later cites the earlier or sits in a special issue of the earlier one's venue (1.0). Authors cite their own earlier papers all the time: a first run counted "cites" for every pair and merged 29 follow-up papers; restricting it to cross-kind pairs and raising the title floor left 6 merges. ≥ 0.85 merges, 0.5 to 0.85 is listed in the report and left apart, below is ignored. Never merged by score: two papers of one edition, and titles with different part numbers ("… I" and "… II"). A shared DOI merges outright (confidence 1.0, method `doi`). Merges are applied best score first and refuse to put two versions of one edition in one work (listed as "blocked"). The earliest version (year, then proceedings before journal, then key) founds the work; the primary version is the journal one if any, then one with a DOI, then the earliest.

**D-75 Registry: a `version` kind with prefix `P`; work IDs anchor on the founding version; a conflicting registry stops the run.** `Kind` gains `version` (`P…`, one per DBLP paper, anchor `("dblp", key)`), because PLAN §4.1 listed no prefix for versions. A work's ID is minted from its founding version's DBLP key; every other version's own work ID is merged into it (`merged_into`), so an ID minted by an earlier run keeps redirecting. If the registry holds a merge that the current rules no longer produce, `resolve` stops with a message rather than reuse or split IDs (hard to undo once a release exists). **Before the first release** the registry is a local file and the way out is to delete `data/warehouse/core_id_registry.parquet` and re-run (done twice in P1-04 while tuning, both times on a run that was never released); after a release a person decides which ID survives.

**D-76 A source record is attached to a paper by §8.1's join order, and rejected when it fails.** DOI (record carries the same DOI), then S2 `externalIds.DBLP` equal to the paper's key, then the OpenAlex ID the lookup found, then the fuzzy rule: title similarity ≥ 0.93 **and** years within 1 **and** the first DBLP author's surname among the words of the record's first author (substring-style containment, because sources write "Buchholz, Thomas", "Sakthi Balan Muthiah", "Lila Kari A" and "Karel Čulík" for "Karel Culík II"). S2 answers carry no authors (D-68), so for S2 the surname rule is waived and the confidence capped at 0.9. A rejected record is dropped and counted; the usual reason is a journal or CoRR version of the paper (year differs), which §8.2 handles. In the pilot: OpenAlex 2,278 papers (4 rejected: authors differ), S2 2,260, Crossref 1,969 of 2,024 with a DOI.

**D-77 Author IDs: OpenAlex mapped onto PIDs, Semantic Scholar not yet.** Per paper the OpenAlex author list is aligned with DBLP's (by position when equal in length and every name agrees, else the best one-to-one name matches); that also gives each DBLP author the affiliation, institution and country OpenAlex has. An OpenAlex ID is linked to a PID when ≥ 2 papers agree and ≥ 80 % of its aligned papers point to that PID, or one paper plus a matching ORCID; otherwise it stays unlinked and is counted in the report. A PID can have several OpenAlex IDs; an OpenAlex ID has at most one PID; two PIDs are never merged (homonyms like "Ann Lee 0001/0002" stay two authors with one display name). **S2 author IDs are not harvested** (P1-03 asked for no `authors` field and changing the field list changes every cache key, about 2 hours of title matches), so `core_author.s2_ids` is empty. Provisional authors for works outside DBLP (§8.3) are not built: every pilot work is in DBLP.

**D-78 Schema additions and choices (amends PLAN §4.2; amends D-70).**
- New `core_version_match(version_id, source, external_id, method, confidence, title_similarity, year_diff, first_author_agrees)`: why each source record is attached (CLAUDE.md rule 4). New `core_version_pair`: every scored version pair that was not ignored, with its features and verdict.
- `core_version.year` is the **edition's** year (the year of the meeting), which is also what a work's year is the minimum of; Crossref's issue date can differ. Pages and volume follow §8.1 (Crossref, then OpenAlex, then DBLP). `url_landing` falls back to `https://doi.org/<doi>`.
- Institutions: ID `ror:<ror>` where OpenAlex gives a ROR, else `openalex:<I…>`; one institution per author and paper (the first OpenAlex lists).
- `is_survey` and `survey_confidence` stay null (PLAN §15.4 fills them later). `scope_*` are set from `config/resolve.yaml`: `core`, 1.0, "tier A venue".
- **`local_abstract` and `local_embedding` keep their `dblp_key` form** (the harvest and embed stages write them before any work exists, and `embed` computes only what lacks a vector per paper). Resolve adds **`local_work_abstract` and `local_work_embedding`, one row per work** (the primary version's row, then the others in key order). Later stages read these two; PLAN §4.2 says `local_abstract(work_id, …)` and `local_embedding(work_id, …)`, which are now these.
- `core_citation` edges are lifted to works (two versions of one work cite as one), self-citations through two versions are dropped, an OpenAlex or S2 ID shared by two different works is skipped (none in the pilot), `is_influential` is null (D-68).

**D-79 Data-quality checks fail loudly (`flatatlas evaluate --data`).** `flatatlas.quality` runs SQL checks on the core tables, stores them in `ops_quality_report` and exits 1 if one fails. Thresholds are in `config/resolve.yaml` (`quality:`): source shares (OpenAlex ≥ 0.90 and S2 ≥ 0.90 of papers; Crossref ≥ 0.95 of papers with a DOI) and at most 150 uncertain pairs, a tripwire (a broken signal gave 460 on the first run; the usual noise is follow-up papers, 93 in the pilot). The tests for the checks are in `tests/data_quality/`.
